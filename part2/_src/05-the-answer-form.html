The answer form

The output type is the form the model fills in: a Python class whose fields the answer must have. The form decides what the model can say. When a real answer doesn't fit, the model squeezes it in and drops the rest, without a doubt in sight.

Three ways to ask for structure

Pydantic AI can request a form in three ways. Tool output offers an output tool, works with tool-calling models, and mixes with other tools. Native output uses the provider's structured-output mode. Prompted output puts the schema in the instructions and parses JSON text. For a list of types, the model picks one through a separate output tool for each type. Validation and retries work the same in all three.

Without a wrapper, the model profile chooses the mode: tool output on most models, native output on Claude models using extended thinking (reasoning before answering), which Sonnet 5.5 uses by default (since 2.52). Pin ToolOutput(...) to use the tool path on every model. On a thinking Claude request, the output tool is offered, not forced; if the model answers in plain text, Pydantic AI retries once and asks for the form.

Go deeper: when prompted output is the right call

Use PromptedOutput when the other modes cannot carry your form: the schema is too large or nested for the provider (some reject deep unions or long enums), the model or gateway stalls or performs worse when the provider enforces the schema, or the model has no tool calling. The model can return JSON with missing fields or wrong types, so validation and retries enforce the form.

Room for doubt

A form can include a way to say "something here doesn't add up". Chapter 6's agent adds doubts: list[str]: "anything in the email that doesn't add up, in your own words". In Part 1 chapter 2, contradictory emails reached a person 30 times out of 30 with a doubts list, and 0 of 30 with a confidence score. Models often give a high confidence score but can name what bothers them. The code sends a non-empty list to a person.

What you can do now

Check ten emails your agent got wrong against its output type: can it represent the right answer? Match the form to what customers say, and add a validator that checks it against your data.

See it in Logfire. The answer form appears in each request's tool definitions. If validation fails, the trace shows the retry request and the validation error sent to the model.

Small print: a validation error goes back as the output tool's result; one retry by default, retries={'output': N} to raise it. When retries run out the run raises UnexpectedModelBehavior and your code decides what a person sees.
