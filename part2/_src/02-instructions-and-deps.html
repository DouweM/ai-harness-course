Instructions and deps

Standing rules go in instructions=. Facts that change go in deps (the data your code passes into each run), and an instructions function writes them onto the page every request. A fact frozen into a string goes stale without anyone noticing.

The date that froze

The point: facts from your app belong in deps and an instructions function, not in an f-string at import. The stakes: a promise recorded for a Friday that already passed.

Tuesday 17 Nov, 09:02Dana's email arrives, and your billing system asks the agent about it. The agent's prompt was written the obvious way: a Python f-string with today's date, built once when the service starts and imports the file. The service started last Thursday and has been running ever since, so the string still says Thursday.

The agent records Friday 13 Nov, a date that already passed, and the reminder schedule sends Dana an overdue reminder on Tuesday afternoon. The model did its job: the page says it is Thursday the 12th, and in Part 1, models given the date on their page worked out the right Friday 15 times out of 15. Nothing failed loudly. The prompt was right on deploy day and has been wrong since.

No prediction here: everyone sees it coming. Spend the time on where the date comes from: the email's arrival, not the clock.

The fix: a fact from deps, every request

{{code ch2_instructions.py deps "code/part2/ch2_instructions.py · deps and an instructions function" keys="received: date|instructions='Decide|@agent.instructions|return f'"}} {{code ch2_instructions.py run "code/part2/ch2_instructions.py, both, side by side"}} {{out ch2_instructions}}

Offline, deterministic. A FunctionModel stands in for the model: it reads the email, then works out "this Friday" from the date on its page, the way models did in Part 1. Use the date the email arrived, a fact your code knows, rather than today's: if your app handles some emails a day late, "this Friday" would point at the wrong week.

When a value changes mid-conversation

An instructions function runs before every request, so its line is always current. For a value that can change while a conversation is open, like month-end close starting on Thursday, give it a name and on_change='append': the old instructions stay as they were, and the change arrives at the end of the page, at the moment it happened. Part 1 chapter 4 showed why: rewriting the top left some models writing like their own past (Grok and Qwen 0 of 24), while appending the change worked on all six models shown, 24 of 24 each. Chapter 3 uses this for a tool that leaves.

What you can do now

Search your prompt code for f-strings and .format(. Every changing value inserted into a prompt becomes a deps field and an instructions function; every value that can change mid-conversation gets a name and on_change='append'.
