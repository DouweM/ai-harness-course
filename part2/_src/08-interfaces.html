Interfaces

The chapter 6 agent works behind every interface: a scheduled job, browser chat, or phone call. What changes is who stores and sends the history. The model believes the history it receives.

One agent, many doors

The point: every interface is a few lines around the same agent. The one decision that matters is who holds the history; the prediction shows a client rewriting it.

Who holds the history

By default, a UI adapter trusts the frontend: the browser sends the conversation each turn, and the agent uses it. This lets the browser decide what history the model sees. For example, the billing team's chat panel could change the lookup result for Dana's invoice to say it is paid. A bug, browser extension, or anyone who can reach the chat URL could do the same.

By default, the browser holds the history and can rewrite tool results or approve a made-up tool call. This may suit a single-user notebook, but not a public endpoint for an agent that can mark invoices paid. Keep history on the server, and check in each writing tool that the signed-in user is allowed to act.

Approvals in the frontend

Chapter 3's approval reaches the UI through the protocol. With AG-UI, a run ends with an interrupt that specifies the question and answer shape. When the billing team asks the agent to record Dana's first payment, nothing is written until someone responds. Approval prevents the model from acting alone, but your server must check that the signed-in person may approve the call. Server-held history also prevents a browser from approving a call the agent never requested.

And the rest

agent.to_web() serves a local chat for trying an agent; to_cli_sync() serves a terminal chat. An MCP server exposes the agent as a tool for other agents. A phone call uses a realtime session on the same agent, collections with billing_world. It uses the same tools and capabilities, and ends with message history you can store or pass to an ordinary run.

{{code ch8_interfaces.py voice_core "A phone call on the same agent, from ch8_interfaces.py"}}

What works the same in a phone call, and what doesn't. Named instructions, such as billing_world's close and ledger lines, accept appended updates during a call. An unnamed instruction function keeps its old text if it changes mid-call, with one warning; session.send(...) delivers an explicit notice. Latency matters: callers hear each lookup pause. On OpenAI and xAI, tools run in the background while the model can keep talking. gpt-realtime-2 already says "let me check" before a tool call, so prompted filler can repeat it. Fetch the slow facts before the call starts. A call cannot pause for approval, so a HandleDeferredToolCalls handler decides each call. It could wait for a person, leaving the caller in silence. Instead, use rules set in advance: approve safe actions and tell callers "a colleague will confirm by email" for the rest. Without a handler, every gated call is refused. End the call with a typed result, like chapter 5's Promise: output_type doesn't apply to a call, so run all_messages() through the ordinary agent afterwards; realtime history is valid input to a run.

If you already run LiveKit, Retell or a phone provider. A Pydantic AI realtime session runs the agent, not the phone line. On your backend, it connects to a speech-to-speech model, holds the agent's tools, capabilities, history and usage limits, and speaks PCM16 audio. Audio transport uses a SIP trunk, WebRTC room, or phone provider's stream. Bridge your existing transport to the session: send caller audio to send_audio (resampled to audio_input_sample_rate) and play stream_audio() into the call. Pydantic AI has no built-in SIP. The same agent then answers the phone, the chat and the batch job.

What you can do now

For each interface, ask who stores the history. If a browser or other service holds it, use manage_message_history='server' or a conversation store.

See it in Logfire. A chat panel run has the same trace as a code run. Check that the first request uses server-stored history.
