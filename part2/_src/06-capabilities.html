Capabilities

Start from the page you want the model to read. Every harness feature adds something to that page at a known moment and in a particular voice; a capability packages additions for any agent. Built-ins and whole agents like Coder use the same approach.

Start from the page you want

The first half of the chapter, about 7 minutes. The point: design the page first (what the model should read, in which voice, from what moment), then pick mechanisms. Every feature in the recipe table is a few insertions at known moments. Then the second half packages them.

The billing app asks the agent to draft a note to Dana: the first half of INV-2041 is due. While the agent looks up the invoice, the bank feed (incoming payments reported by your bank) shows her wire, a bank transfer, as incoming but not yet confirmed. Part 3 records the confirmation.

Before any code, write down the page you want the model to read when it writes that note. Here it is, simplified, in the order the model reads it:

// the page we want the model to read
instructions
You handle customers' emails about their invoices with us, and record what they promise. Amounts and invoice numbers come from our billing system, never from an email alone. Month-end close is running until Monday: mark_paid is unavailable, so say so. This message was received on Friday 2026-11-20.
tool definitions
read_email, lookup_invoice, record_payment (mark_paid: off the page during close)
user: the billing app
INV-2041: the first half, 2,060.00, is due today. Draft today's note to Dana.
model → tool call
lookup_invoice(invoice_number='INV-2041')
tool result: lookup_invoice
INV-2041: 4120.00 USD, open

Changes in our ledger since this conversation started: Bank feed, INV-2041: incoming wire of 2,060.00, not yet confirmed.

Promise, or a plain reply

Each line has a voice (Part 1, chapter 3) and an arrival point. Instructions and tool definitions come from your app; its request uses the user voice. The lookup result is data. The incoming wire is a system fact, so your app adds it in the operator's voice during the run (Part 1, chapter 4).

For each fact, decide who says it and when it arrives. The rest of this chapter covers where Pydantic AI lets you add it.

Where things go in, and when

A run loops through model requests, tool calls, and results. You can add to or change the page at these moments:

MomentWhat you can put on the page, or changeIn Pydantic AI
Before the runThe history you load (chapter 4), and the user's messageconversation=, the prompt
Before every requestThe instructions, read again: a changed one either rewrites the start of the page or is appended at the end@instructions(on_change='append')
Which tools this request offersprepare=, prepare_tools
The model and its settingsget_model, get_model_settings
The messages actually sent: clear, cut or summarize old onesbefore_model_request, history processors
A system message for this request only, at the endSystemReminders
During a tool callThe result, as data. A message the tool adds with ctx.enqueue goes right after its resultthe return value, ctx.enqueue(...)
Any time, from outsideA message into the running run, before its next requestrun.enqueue(...)
When the model gives its final answerQueued content that gives it another turn; a check that sends the answer back; a call that waits for a personpriority='when_idle', ModelRetry, DeferredToolRequests
Between runsWhat you store, and what changed since the last runresult.conversation, appended instruction changes

Keep the page's start unchanged so the provider can reuse its cache and earlier reasoning still applies. Add changes at the end. Use the right voice: your system states ledger changes; a tool reads email as data.

Between one request and the next, all of this can change:

  • Instructions: a notice that appears, changes or goes away (this one, chapter 3's close notice).
  • Tools: if close starts mid-run, mark_paid is gone from the next request. A tool search can reveal tools, and loading an on-demand capability adds its tools and instructions together.
  • The model and its settings: chosen per request, or swapped for the next model when a request fails.
  • The messages sent: old results cleared or summarized as the page fills up (chapter 4).
  • New messages: a tool's follow-up, a background result, a message from another agent or your app.

Don't rewrite what the model already read. That makes the provider process everything again and leaves earlier turns answering text that is no longer there. State changes at the end.

Every feature is a recipe

Each feature adds something to the page at a particular moment and in a particular voice. Common examples:

FeatureWhat it puts on the page, and whenWhere
NoticesA changed instruction, appended at the end before the next request, in your voice (chapter 3, and the wire above)on_change='append' core
Hiding a toolLeaves its definition out of a request. Pair it with a notice, or the model doesn't know why (chapter 3)prepare= core
ApprovalsThe call is on the page; the run pauses. The person's decision comes back as that call's result on the next run, or a policy decides within the runrequires_approval, HandleDeferredToolCalls core
RemindersA system message at the end of one request, gone from the next, so a long run doesn't drift from a ruleSystemReminders harness
Background toolsThe call's result is "started" with a task id. The real result arrives later as a message framed as that tool's result; the run waits for it before it endsBackgroundTools harness
Agents messaging agentsA delegated task's report and questions arrive as messages framed as task data. A message to a running task is read at its next requestSubAgents with TaskControl harness
ClearingReplaces an old tool result with a note; the call stays, so the model can fetch it again (chapter 4)ClearToolResults harness
CompactionReplaces older turns with one summary (chapter 4)TieredCompaction harness
Tool searchHolds tool definitions back; a search puts the matches on the next requestToolSearch, defer_loading=True core
On-demand capabilitiesA one-line catalog entry. Loading one states its instructions as a system message and adds its toolsdefer_loading=True on a capability core
Code modeFolds tools into one run_code tool. The model writes a program that calls them; only what it returns reaches the pageCodeMode harness
FallbackThe same page, sent to the next model when a request fails or is refusedModelFallback core

For any feature, ask what it puts on the page, in whose voice, when, and how the model gets the rest. These answers help you predict its behavior and build your own when needed.

Making room: the context tricks

Every request includes the whole page. Models choose less well when it grows long or the tool list has a few dozen entries. Each trick below hides content; consider how the model retrieves it and at what cost.

TrickWhat stays off the pageHow the model gets it backThe catch
Clearing (chapter 4)Old tool resultsCalls the tool againOnly for results a tool can fetch again: not Dana's emails
Compaction (chapter 4)Older turnsIt can't; it has the summaryLossy: keep rules and promises word for word
Tool output limitsMost of a huge resultPages through a saved copy, if you keep oneThe model must know there's more
Tool searchDefinitions of tools it hasn't neededSearches by keywordOne more round trip; it has to guess the words
On-demand capabilitiesWhole workflows: instructions, tools, settingsLoads one by nameCosts a round trip: skip it for what most runs need
Code modeIntermediate resultsNever needs them: its code filters themThe model must write correct code, in a sandbox's subset of Python
Sub-agents (chapter 7)A whole sub-task's workReads the reportThe report is all it knows

Clearing and compaction change earlier content, restarting the provider's cache. Use them in larger steps when the page is nearly full. Other tricks add content at the end and keep the cache. The billing world, packaged

Capability has the same decorators as an agent, so moving code over changes its prefix. The full file packages the received date (chapter 2), the close notice and gated mark_paid (chapter 3), and errors that identify whose problem they are. record_payment also requires approval and checks arguments with args_validator=, so invalid calls are rejected before approval. Chapters 7 to 9 and Part 3 import this file. Capabilities can also add model settings, fallback models, history processing, and hooks around requests and tool calls.

Building blocks for your own

There are three ways to build one: use Capability(...) with decorators; use Hooks() and @hooks.on.<event> for a lifecycle hook, such as an audit log on one agent; or inherit from AbstractCapability when a rule needs configuration, tests, or its own package. A Hooks capability can replace an agent subclass or wrapper used for logging or guards, and works on every agent. Any capability can load on demand with an id and defer_loading=True.
