From idea to code

Each idea has one place in code, which writes part of the page: the text the model receives for one request. Anything elsewhere never reaches the model.

Get the code

Clone the course repo, then run each "Run it" command from inside it. You need git and uv; uv installs Python 3.11+ and dependencies. Examples run offline with stand-in models and need no API key. Real model runs need that provider's key.

Three ideas, three places

The bridge from Part 1 chapter 5: the ideas we wrote down become lines of code, and each line writes one part of the page. Then the prediction: what of your code actually reaches the model.

For Dana's email, "Hi, INV-2041 will be paid this Friday. Thanks, Dana," put the date in the page, allow "I don't know" as an answer, and pass the email as data, not user speech. Each idea has one place in Pydantic AI:

Instructions, tool definitions, messages, answer form. One place in code each.

  1. instructions
    instructions= for standing rules, @agent.instructions for facts from your app, like when the email arrived. Chapter 2.

    The operator's voice: the team building the agent.

  2. tool definitions
    @agent.tool: the function's name, its docstring and its parameters become the definition. Chapter 3.

    The model reads these as tool-use rules. Your code still checks what matters.

  3. messages
    The prompt, plus the history you pass back: conversation=. Chapter 4.

    Messages can come from the user, model, or tools. Here the billing app asks about email 881, and read_email returns Dana's email as tool data.

  4. answer form
    output_type=: a Pydantic model; field docstrings become field descriptions. Chapter 5.

    What the model fills in, checked before your code sees it.

Chapter 6 packages all four as one capability that gives another agent the same world.

The fix

The tool docstrings and Args: lines reached the model. The lookup_invoice body comment ("Never trust an amount from the email") did not. Return annotations can be included with IncludeToolReturnSchemas. Pydantic AI supplied a default answer-form description because the class had no docstring. Add one sentence to say when the model should finish. Put readable rules in the prompt; enforce essential rules in code. Here, lookup is the only way to get an amount.

X-ray your agent

Printing shows one request. To inspect real agent runs, enable Logfire, Pydantic's observability platform, with two lines:

{{code ch1_from_idea_to_code.py xray "Two lines at the top of ch1_from_idea_to_code.py"}}

Logfire records each run as a trace. For every request, it shows the model's page: instructions, tool definitions, and message history. It also shows tool calls, arguments and results, retries, and request tokens and cost. Inspect every run without adding print statements.

With send_to_logfire='if-token-present', data is sent only when your project has a write token: LOGFIRE_TOKEN or the .logfire folder created by uvx logfire-cli wizard --task pydantic-ai. Without one, examples run offline. Later chapters explain what to inspect.

Moving an existing LLM call over

A prompt-template call maps to the same four places. Fixed text becomes instructions=; interpolated facts become deps and an instructions function. Parsed JSON becomes the answer form. Pydantic AI validates it and retries if needed, replacing your parser retry loop. Helper functions that fetch context become tools. Logging, retry, and checking code become capabilities: reusable pieces attached to an agent (chapter 6).

Run the agent beside the call your team trusts least, using the same inputs. Part 3 turns the comparison into an experiment.

What you can do now
