Part 1 gave us ideas for this email: put the date on the page, let the answer say "I don't know", and hand Dana's words to the model as data, not as the user speaking. In Pydantic AI each one lands in exactly one place, in the order the page is built:

Instructions, tool definitions, messages, answer form. One place in code each.

  1. instructions
    instructions= for standing rules, @agent.instructions for facts from your app, like when the email arrived. Chapter 2.

    The operator's voice.

  2. tool definitions
    @agent.tool: the function's name, its docstring and its parameters become the definition. Chapter 3.

    Also the operator: the model reads them as a contract.

  3. messages
    The prompt, plus the history you pass back: conversation=. Chapter 4.

    The user, the model, and data from tools. Here the user is your billing system, asking about email 881; Dana's email comes back from read_email as a tool result. That is Part 1 chapter 3's idea in code.

  4. answer form
    output_type=: a Pydantic model; field docstrings become field descriptions. Chapter 5.

    What the model fills in, checked before your code sees it.

Chapter 6 then packages all four as one capability, so a second agent gets the same world.

The fix

Read the output once more. The tools' docstrings and Args: lines made it; the comment in lookup_invoice's body ("Never trust an amount from the email") did not, and neither did the return annotation (it can, with the IncludeToolReturnSchemas capability). The answer form's description came from the framework, because the class had no docstring: one sentence on the class replaces it, and it's the best place to say when the model should finish. A rule the model must follow goes where it can read it; a rule that must hold no matter what the model reads goes in code: here, the lookup is the only way the agent gets an amount at all.

Moving an existing call over

A prompt-template call maps onto the same four places. The template's fixed text becomes instructions=. Its interpolated facts become deps and an instructions function. The JSON you parse becomes the answer form, and the retry loop around the parser goes away. Helper functions you call before the prompt, to fetch what the model might need, become tools. The logging, retry and guard code around the call becomes capabilities.

Start with the call your team trusts least, run the agent beside it on the same inputs, and compare. Part 3 turns that comparison into an experiment.
