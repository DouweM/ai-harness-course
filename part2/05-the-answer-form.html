The answer form

The output type is the form the model fills in: a Python class whose fields the answer must have. The form decides what the model can say. When a real answer doesn't fit, the model squeezes it in and drops the rest, without a doubt in sight.

The fix: a form that holds it, checked against your invoice records

The form: one row per installment, from ch5_answer_form.py
class Installment(BaseModel):
    amount: Decimal
    due_date: date


class Promise(BaseModel, use_attribute_docstrings=True):
    is_commitment: bool
    invoice_number: str | None = None
    installments: list[Installment] = []
    """One per amount and date the customer promised. A single payment is one installment."""
The check against your ledger, on the same agent
@agent.output_validator  # facts the form can't check on its own: they need your ledger
async def matches_the_ledger(ctx: RunContext[Deps], promise: Promise) -> Promise:
    if promise.invoice_number:
        invoice = await ctx.deps.billing.get_invoice(promise.invoice_number)
        if invoice is None:
            raise ModelRetry(f'There is no invoice {promise.invoice_number}. Leave it empty if unsure.')
        total = sum((i.amount for i in promise.installments), Decimal(0))
        if total > invoice.amount:
            raise ModelRetry(f'{invoice.number} is for {invoice.amount}; the installments add up to {total}.')
    return promise

The type checks that the answer has the right fields and types. The output validator catches facts that need your systems, like installments that add up to more than the invoice, and sends the model back with the real balance. The error becomes the next message; nobody writes a retry loop:

Three ways to ask for structure

Pydantic AI can ask the model for the same form in three ways. Tool output offers an output tool to call, works with every tool-calling model and mixes freely with other tools. Native output uses the provider's own structured-output mode. Prompted output puts the schema in the instructions and parses JSON text. Give a list of types and the answer can be any one of them: one output tool per type, and the model picks. Validation, validators and retries work the same in all three.

Without a wrapper, the model profile picks: tool output on most models, but native output on Claude models when the request uses extended thinking (reasoning before answering), which Sonnet 5.5 does by default (since 2.52). Pin ToolOutput(...) to keep the tool path on every model, as this course does (on a thinking Claude request the output tool is offered rather than forced, so if the model answers in plain text instead, Pydantic AI spends one retry asking for the form).

code/part2/ch5_answer_form.py, the three modes
from pydantic_ai import NativeOutput, PromptedOutput

tool_form = ToolOutput(Promise)  # the model "calls" a final_result tool: works with every tool-calling model
native_form = NativeOutput(Promise)  # the provider's own structured-output mode
prompted_form = PromptedOutput(Promise)  # the schema goes in the instructions; the model answers in JSON text
either = [Promise, str]  # a union: the model can also answer in plain text

Go deeper: when prompted output is the right call

Reach for PromptedOutput when the other two can't carry your form: a schema too large or too nested for a provider's structured-output mode (some reject deep unions or long enums outright), a model or gateway that stalls or gets worse when the provider forces its output to follow the schema, or a model with no tool calling at all. You trade enforcement for reach: the model can write JSON with missing fields or wrong types, so validation and retries do the enforcing.

Room for doubt

A form decides what the model can say, and that includes "something here doesn't add up". Chapter 6's agent carries one more field, doubts: list[str], "anything in the email that doesn't add up, in your own words". It's the field Part 1 chapter 2 measured: contradictory emails reached a person 30 times out of 30 with a doubts list, and 0 of 30 with a confidence score, because a model writes 95 on almost anything but will name what bothers it. Your code acts on it: a non-empty list goes to a person.
