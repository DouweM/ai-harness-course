Who holds the history

By default a UI adapter trusts the frontend: the browser sends the whole conversation each turn, and the agent runs on it. That's convenient, and it means the browser decides what history the model sees. Here the billing team's chat panel sends Tuesday's conversation back to your server with one edit: the invoice lookup's result now says the invoice is paid. A bug, a browser extension or anyone who can reach your server's chat URL can send that.

What the model read

The edited one. To the model it's its own lookup, and Part 1 showed it believes every line of its history.

// output
manage_message_history='client': the lookup on the model's page says 3900.00, paid

Under the default the browser holds the history, so it can rewrite what your tools returned, and even approve a tool call it made up itself. Fine for a single-user notebook; not for an endpoint any browser can reach, in front of an agent that can mark invoices paid. Keep the history on the server, and check inside each writing tool that the signed-in user may do it.

The fix: the server holds the history

Approvals in the frontend

Chapter 3's approval reaches a UI as part of the protocol. With AG-UI the run finishes with an interrupt: what to ask, and the shape of the answer. Friday afternoon the billing team asks the agent to record Dana's first half; nothing is written until someone answers. Approval stops the model acting alone, but it doesn't check who answers: your server must check that the signed-in person may approve this call. Keeping the history on the server, as above, also means a browser can't approve a call the agent never asked for.

code/part2/ch8_interfaces.py, an approval over AG-UI
from pydantic_ai.ui.ag_ui import AGUIEventStream


async def asks_to_record(messages: list[ModelMessage], info: AgentInfo):
    args = '{"invoice_number": "INV-2041", "amount": "2060.00"}'
    yield {0: DeltaToolCall(name='record_payment', json_args=args, tool_call_id='call_1')}


async def what_the_frontend_gets() -> None:
    stream = AGUIEventStream(thread_id='dana', run_id='friday')
    deps = Deps(billing=FakeBilling(), received=WIRE_RECEIVED)
    with collections.override(model=FunctionModel(stream_function=asks_to_record)):
        async with collections.run_stream_events("Dana's first half arrived: record 2,060.00 on INV-2041.", deps=deps) as events:
            async for event in stream.transform_stream(events):
                last = event
    for interrupt in last.outcome.interrupts:  # the run is over, and says why: a person has to approve
        print(' ', interrupt.message, interrupt.response_schema['required'])
    print('ledger writes:', deps.billing.writes)


asyncio.run(what_the_frontend_gets())
// output

And the rest

agent.to_web() serves a local chat for trying an agent; to_cli_sync() a terminal one. An MCP server can expose the agent as a tool for other agents. And a phone call is a realtime session on the same agent, collections with billing_world: one realtime session for the whole call, the same tools and capabilities, and at the end a normal message history you can store or pass to an ordinary run.

A phone call on the same agent, from ch8_interfaces.py
async def small_amounts(ctx: RunContext[Deps], requests: DeferredToolRequests) -> DeferredToolResults | None:
    """A caller hears the silence while a person decides, so decide by policy: approve up to 1,000, refuse the rest."""
    small = {c.tool_call_id: True for c in requests.approvals if Decimal(str(c.args_as_dict().get('amount', 0))) <= 1000}
    return requests.build_results(approvals=small) if small else None  # refused: "a colleague will confirm by email"


async def call(caller_audio: AsyncIterator[bytes], deps: Deps) -> list[ModelMessage]:
    """One phone call, one session: the same agent and billing_world as every other door."""
    session_for = collections.realtime(
        'openai:gpt-realtime-2', deps=deps, capabilities=[HandleDeferredToolCalls(small_amounts)]
    )  # no handler: every approval-gated call is refused mid-call. output_type doesn't apply to a call.
    async with session_for.session() as session:

        async def listen() -> None:
            await session.send_audio(caller_audio)  # mono PCM16 at session.audio_input_sample_rate; returns at hang-up
            await session.close()  # the caller hung up: end the session, which ends the loop below

        listening = asyncio.create_task(listen())
        async for event in session:  # until the session closes
            ...  # speech out (session.stream_audio() is the audio stream back), tool calls, turn boundaries
        listening.cancel()
        return session.all_messages()  # ordinary history: store it, or turn it into a typed Promise

What works the same in a phone call, and what doesn't. Appending changes works the same for a named instruction, like billing_world's close and ledger lines: a change mid-call goes out as an appended update, not a rewritten prompt (an unnamed instruction function that changes mid-call keeps its old text, with one warning; session.send(...) delivers an explicit notice). Latency is the new constraint: every lookup is a pause the caller hears. On OpenAI and xAI, tools run in the background and the model can keep talking, and gpt-realtime-2 already says a short "let me check" before a tool call, so prompting your own filler can make it say it twice. Fetch the slow facts before the call starts. A call has nowhere to pause for approval: a HandleDeferredToolCalls handler decides each one during the call. It could wait for a person, but the caller would sit in silence, so decide by rules set in advance instead: approve what's safe, and turn the rest into "a colleague will confirm by email". Without a handler, every gated call is refused. And the call should end with a typed result, like chapter 5's Promise: output_type doesn't apply to a call, so run all_messages() through the ordinary agent afterwards; realtime history is valid input to a run.

If you already run LiveKit, Retell or a phone provider. A Pydantic AI realtime session is the agent, not the phone line. It holds the connection to a speech-to-speech model on your backend, together with the agent's tools, capabilities, history and usage limits, and it speaks PCM16 audio. Getting the call's audio to and from it is a transport job: a SIP trunk, a WebRTC room, or a phone provider's audio stream. If you already run that transport, keep it and bridge it to the session: feed the caller's audio to send_audio (resampled to audio_input_sample_rate), and play stream_audio() back into the call. Pydantic AI has no built-in SIP. The same agent then answers the phone, the chat and the batch job.

What you can do now

For each interface your agent sits behind, ask who stores the history. If it's a browser or another service, switch to manage_message_history='server' or a conversation store.
