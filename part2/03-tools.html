Tools

The model decides whether to call a tool. Your code decides which tools a request offers, which ones wait for a person, and what the model hears back. If your code takes a tool away without saying why, the model is left guessing.

Three rules for tools: when they're offered, who approves, what errors say

The point: three decisions in code, one line each. Then the gate that holds but says nothing, and the one line that fixes it on the same page.

Thursday 19 Nov, 09:00Month-end close starts: the finance team freezes the books until Monday. Looking invoices up is always fine. Marking one paid needs a person's approval, and during close it isn't allowed at all. (Recording money that arrived, record_payment, gets its own approval in chapter 6.)

Each rule is about one line of code: prepare= decides per request whether a tool is offered, requires_approval=True turns a call into a question for a person, ModelRetry turns a bad argument into feedback, and ctx.tool_call_id makes the write safe to retry.

Offered or not: prepare. Runs or waits: requires_approval. Talks back: ModelRetry.

The agent and its three rules, from ch3_tools.py
agent = Agent(
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions="You handle customers' emails about their invoices with us.",
    output_type=[str, DeferredToolRequests],  # a run can end by asking a person to approve a call
)


@agent.tool
async def lookup_invoice(ctx: RunContext[Deps], invoice_number: str) -> Invoice:
    """Look up one of our invoices: amount, currency and status."""
    invoice = await ctx.deps.billing.get_invoice(invoice_number)
    if invoice is None:
        raise ModelRetry(f'There is no invoice {invoice_number}. Check the number in the email.')
    return invoice


async def hide_during_close(ctx: RunContext[Deps], tool_def: ToolDefinition) -> ToolDefinition | None:
    return None if ctx.deps.closing else tool_def  # None: this request doesn't offer the tool


@agent.tool(requires_approval=True, prepare=hide_during_close)  # a person decides; gone during close
async def mark_paid(ctx: RunContext[Deps], invoice_number: str) -> str:
    """Mark one of our invoices as paid."""
    await ctx.deps.billing.mark_paid(invoice_number, idempotency_key=ctx.tool_call_id)  # safe to retry
    return f'{invoice_number} is marked as paid.'

The tool that left

Thursday, during close, a colleague who misread Dana's Tuesday email asks the agent to mark INV-2041 paid. The model used mark_paid on Wednesday, for another invoice, so it tries again. Step through what happens.

  1. 1
    model → tool call
    mark_paid({"invoice_number": "INV-2041"})
  2. ×
    back to the model: your code didn't offer it
    model reads: {"error":"Unknown tool name: 'mark_paid'. Available tools: 'lookup_invoice'"}
  3. 2
    the reply drafted for Dana
    model says:  I wasn't able to mark INV-2041 as paid. Please try again later.
  4. +
    add one line, appended when close starts
    Month-end close is running until Monday: mark_paid is unavailable, so say so.
  5. ✓
    the reply drafted for Dana now
    model says:  Month-end close is running, so I can mark INV-2041 paid on Monday.

Nothing was written either time, because the tool wasn't offered (ledger writes: []). What changed is what the model could tell the customer. "Please try again later" is wrong on Thursday and Friday, so Dana is told to try again. This is Part 1 chapter 2's tool that was removed without a word: none of 80 conversations noticed on their own, and one line saying so fixed it on most models. When the tool is hidden and nobody says so, models may also reach for a different tool to get the same result: Part 3, chapter 4 probes it.

code/part2/ch3_tools.py, the line · pydantic-ai 2.59+
@agent.instructions(name='close', on_change='append')  # say why, on the page, when it changes
def close_notice(ctx: RunContext[Deps]) -> str | None:
    if ctx.deps.closing:
        return 'Month-end close is running until Monday: mark_paid is unavailable, so say so.'
    return None

Offline, deterministic. The "Unknown tool" result and the ledger writes are Pydantic AI 2.68's real behavior. The replies come from a stand-in model that answers from its page; what real models did with each page is Part 1 chapter 2's measurement.

A person approves the call first

With requires_approval=True the tool never runs on the model's say-so. The run ends with DeferredToolRequests as its output, listing the calls that wait. Nothing keeps running while it waits: your app stores the conversation (chapter 4), shows the request to a person, and when they answer, minutes or days later, starts a new run with the stored conversation and deferred_tool_results=. Chapter 8 shows how a frontend renders it, and Part 3 how it survives a weekend.

Errors that say who has to fix it

Friday, Dana wires the first half. Recording it can fail three ways, and the model needs to know which, because it decides what to tell her:

What went wrongRaiseWhat the model does
Its mistake: an unknown invoice, a bad amountModelRetryFixes the call and tries again, within the tool's retry budget
Your system failed: the ledger timed outToolFailedTells the customer it will be recorded later; recorded as failed on your traces
A normal answer, even a "no"return a stringReads it as data
code/part2/ch3_tools.py, three worlds
from decimal import Decimal

from pydantic_ai import ToolFailed

from billing import WIRE_RECEIVED, LedgerUnavailable


@agent.tool
async def record_payment(ctx: RunContext[Deps], invoice_number: str, amount: Decimal) -> str:
    """Record a payment we received against one of our invoices."""
    if await ctx.deps.billing.get_invoice(invoice_number) is None or amount <= 0:
        raise ModelRetry('Use one of our invoice numbers and a positive amount, like 2060.00.')  # its mistake
    try:
        return await ctx.deps.billing.record_payment(invoice_number, amount, idempotency_key=ctx.tool_call_id)
    except LedgerUnavailable:  # our outage: not the model's to fix, and nothing happened
        raise ToolFailed('Nothing was recorded: the ledger is unavailable. Tell the customer it will be recorded later.')
// output

ledger down: failed  {"error":"Nothing was recorded: the ledger is unavailable. Tell the cu

Returning "error: ledger down" as a string is the old way: the model may still say it worked, and your monitoring counts the call as a success, because the function returned normally.

What you can do now

Gate every writing tool with requires_approval or prepare, key every write on ctx.tool_call_id, and say on the page why a tool is gone. Sort your tools' failures into ModelRetry, ToolFailed and normal answers.

Small print: a ModelRetry counts against the tool's retry budget (1 by default); ToolFailed doesn't, so bound repeats with usage limits. Toolsets group tools you reuse, filter or swap as one unit; an MCP server's tools reach the model exactly like yours.
