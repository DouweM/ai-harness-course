Instructions and deps

Standing rules go in instructions=. Facts that change go in deps, and an instructions function writes them onto the page every request. A fact frozen into a string goes stale without anyone noticing.

The date that froze

The point: facts from your app belong in deps and an instructions function, not in an f-string at import. The prediction has real stakes: a promise recorded for a Friday that already passed.

Tuesday 17 Nov, 09:02Dana's email arrives. The agent's prompt was written the obvious way: an f-string with today's date, built when the module loads. The service was deployed last Thursday and hasn't restarted since.

from pydantic import BaseModel

from pydantic_ai import Agent, ToolOutput


class PaymentCommitment(BaseModel):
    is_commitment: bool
    invoice_number: str | None = None
    due_date: date | None = None


STARTED = date(2026, 11, 12)  # the service was deployed last Thursday; stands in for date.today() at import

baked = Agent(
    'anthropic:claude-sonnet-5-5',
    instructions=f'Decide whether this customer email commits to paying us. Today is {STARTED:%A %Y-%m-%d}.',
    output_type=ToolOutput(PaymentCommitment),
)

The fix: a fact from deps, every request

code/part2/ch2_instructions.py · deps and an instructions function
from dataclasses import dataclass

from pydantic_ai import RunContext

from billing import FakeBilling


@dataclass
class Deps:
    billing: FakeBilling
    received: date  # when this email arrived: a fact your code knows, per run


agent = Agent(
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions='Decide whether this customer email commits to paying us.',  # standing rules: static
    output_type=ToolOutput(PaymentCommitment),
)


@agent.instructions  # rebuilt for every request, from this run's deps
def when_it_arrived(ctx: RunContext[Deps]) -> str:
    return f'The email was received on {ctx.deps.received:%A %Y-%m-%d}.'

Offline, deterministic. A FunctionModel stands in for the model and works out "this Friday" from the date on its page, the way models did in Part 1. Use the date the email arrived, a fact your code knows, rather than today's: a queue that works through yesterday's mail would pick the wrong week.

When a value changes mid-conversation

An instructions function runs before every request, so its line is always current. For a value that can change while a conversation is open, like month-end close starting on Thursday, give it a name and on_change='append': the old instructions stay as they were, and the change arrives at the end of the page, at the moment it happened. Part 1 chapter 4 showed why: rewriting the top left some models writing like their own past (Grok and Qwen 0 of 24), while appending the change worked on all six models tested (24 of 24). Chapter 3 uses this for a tool that leaves.

code/part2/ch2_instructions.py, a value that changes · pydantic-ai 2.59+
@dataclass
class CloseDeps(Deps):
    closing: bool = False  # month-end close is running


agent_with_close = Agent('anthropic:claude-sonnet-5-5', deps_type=CloseDeps, instructions='Handle this customer email.')


@agent_with_close.instructions(name='close', on_change='append')  # a value that can change mid-conversation
def close_notice(ctx: RunContext[CloseDeps]) -> str | None:
    return 'Month-end close is running: invoices cannot be marked paid until Monday.' if ctx.deps.closing else None

What you can do now

Grep your prompts for f-strings and .format(. Every interpolated fact becomes a deps field and an instructions function; every value that can change mid-conversation gets a name and on_change='append'.
