From idea to code

Part 1 ended with ideas for Dana's email. Every idea has one place in code, and each place writes one part of the page. Anything you put elsewhere never reaches the model.

Three ideas, three places

The bridge from Part 1 chapter 5: the ideas we wrote down become lines of code, and each line writes one part of the page. Then the prediction: what of your code actually reaches the model.

Tuesday 17 Nov, 09:02"Hi, INV-2041 will be paid this Friday. Thanks, Dana." Part 1 gave us ideas for this email: anchor the date, let the answer say "I don't know", fetch the amount instead of trusting the email. In Pydantic AI each one lands in exactly one place, in the order the page is built:

Instructions, tool definitions, messages, answer form. One place in code each.

  1. instructions
    instructions= for standing rules, @agent.instructions for facts from your app, like when the email arrived. Chapter 2.

    The operator's voice.

  2. tool definitions
    @agent.tool: the function's name, its docstring and its parameters become the definition. Chapter 3.

    Also the operator: the model reads them as a contract.

  3. messages
    The prompt, plus the history you pass back: conversation=. Chapter 4.

    The user, the model, and data from tools.

  4. answer form
    output_type=: a Pydantic model; field docstrings become field descriptions. Chapter 5.

    What the model fills in, checked before your code sees it.

Chapter 6 then packages all four as one capability, so a second agent gets the same world.

code/part2/ch1_from_idea_to_code.py
from dataclasses import dataclass
from datetime import date

from pydantic import BaseModel

from pydantic_ai import Agent, RunContext, ToolOutput

from billing import FakeBilling, Invoice


class PaymentCommitment(BaseModel, use_attribute_docstrings=True):  # the answer form
    is_commitment: bool
    """True only if the sender promises to pay."""
    invoice_number: str | None = None
    due_date: date | None = None
    """Leave empty if the email doesn't let you work it out."""


@dataclass
class Deps:  # facts your code knows, carried into each run
    billing: FakeBilling
    received: date


agent = Agent(
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions='Decide whether this customer email commits to paying us.',  # the operator's voice
    output_type=ToolOutput(PaymentCommitment),
)


@agent.instructions  # a fact from your app, on the page every request
def when_it_arrived(ctx: RunContext[Deps]) -> str:
    return f'The email was received on {ctx.deps.received:%A %Y-%m-%d}.'


@agent.tool
async def lookup_invoice(ctx: RunContext[Deps], invoice_number: str) -> Invoice | None:
    """Look up one of our invoices: amount, currency and status.

    Args:
        invoice_number: As written in the email, like INV-2041.
    """
    # Never trust an amount from the email: always use this lookup.
    return await ctx.deps.billing.get_invoice(invoice_number)

code/part2/ch1_from_idea_to_code.py, printing the page
from pydantic_ai.messages import ModelMessage, ModelResponse, ToolCallPart
from pydantic_ai.models.function import AgentInfo, FunctionModel

from billing import DANA, RECEIVED


def print_the_page(messages: list[ModelMessage], info: AgentInfo) -> ModelResponse:
    print('instructions:', info.instructions)
    for tool in info.function_tools + info.output_tools:
        print(f'tool {tool.name}: {tool.description!r}')
        for name, field in tool.parameters_json_schema['properties'].items():
            print(f'  {name}: {field.get("description", "")!r}')
    print('user:', messages[-1].parts[-1].content)
    return ModelResponse(parts=[ToolCallPart(info.output_tools[0].name, {'is_commitment': True})])


with agent.override(model=FunctionModel(print_the_page)):
    agent.run_sync(DANA, deps=Deps(billing=FakeBilling(), received=RECEIVED))

Offline, deterministic. A FunctionModel stands in for the model and prints what it was given; with a real model the provider gets the same contents in its own format.

The fix

A rule the model must follow goes where it can read it: in the instructions if it applies everywhere, in the tool's docstring if it is about that tool. And a rule that must hold no matter what the model reads goes in code: here, the lookup is the only way the agent gets an amount at all. Notice also the answer form's own description, "The final response which ends this conversation": a docstring on the class replaces it.

Most rooms pick B. People put rules in comments and function bodies and wonder why the model ignores them. Land: the page is instructions, tool definitions, messages, answer form, and nothing else.

Moving an existing call over

A prompt-template call maps onto the same four places. The template's fixed text becomes instructions=. Its interpolated facts become deps and an instructions function. The JSON you parse becomes the answer form, and the retry loop around the parser goes away. Helper functions you call before the prompt, to fetch what the model might need, become tools. The logging, retry and guard code around the call becomes capabilities.

Start with the call your team trusts least, run the agent beside it on the same inputs, and compare. Part 3 turns that comparison into an experiment.

What you can do now

Print what your agent's model receives on one request, and read it top to bottom. Every rule your team relies on should be on that page, or enforced in code.
