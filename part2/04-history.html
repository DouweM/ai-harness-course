History

Part 1 said its history is its world. In code, that history is a list you store and pass back, and when it gets too long, how you make room decides what the model still knows.

Tuesday to Thursday, stored

The point: you own the list. Store the whole conversation; when it gets long, clear tool results with a stub instead of cutting messages. The prediction shows what cutting loses.

Each run starts from what you pass it. Store result.conversation per conversation, load it on the next email, maybe in another process, and pass it back. Three days of Dana's thread:

code/part2/ch4_history.py
from pydantic_ai import ConversationTypeAdapter

agent = make_agent()
database: dict[str, bytes] = {}  # yours: a table keyed by conversation id

with agent.override(model=FunctionModel(looks_up_then_answers)):
    for day, email in [(RECEIVED, DANA), (CORRECTION_RECEIVED, CORRECTION), (CLOSE_STARTS, 'Is INV-2041 still open?')]:
        stored = database.get('dana')
        conversation = ConversationTypeAdapter.validate_json(stored) if stored else None  # maybe another process
        result = agent.run_sync(email, deps=Deps(FakeBilling(), day), conversation=conversation)
        database['dana'] = ConversationTypeAdapter.dump_json(result.conversation)  # store the whole thing

print('stored messages by Thursday night:', len(result.all_messages()))

Friday: making room

Friday 20 Nov, 10:30Dana writes that the first half is on its way. In production the thread is now long, and every request pays for all of it. Something has to go. The old workaround is a history processor that keeps the last few messages; the Harness's ClearToolResults blanks old tool results instead.

code/part2/ch4_history.py, the old way
from pydantic_ai.capabilities import ProcessHistory

keep_the_last_four = ProcessHistory(lambda messages: messages[-4:])  # the old workaround: cut from the front
code/part2/ch4_history.py, clearing old results · pydantic-ai-harness 0.68
from pydantic_ai_harness.compaction import ClearToolResults

clear_old_results = ClearToolResults(
    max_messages=8,  # in production: max_fraction=0.7 of the model's window
    keep_pairs=1,  # the newest lookup stays
    placeholder='[Cleared to save space. Call lookup_invoice again if you need it.]',  # a stub, not a hole
)

Cut to the last four, the page opens on a tool call the model made with no request before it, which some providers reject outright, and the model no longer knows the payment is split: Friday's 2,060 looks like a short payment. Cleared, every message stays, and the old lookups become a note saying how to get them back.

Offline, deterministic. Both pages are what Pydantic AI 2.68 and the Harness 0.68 actually send. How models treat a missing result is measured: whether it was deleted or replaced by a stub, four hosted models looked the fact up again, 160 times out of 160; deleting without a stub also made Sonnet 5.5 disown its own earlier answers (Part 1 chapter 2). A smaller open-weight model is another story; Part 3 chapter 2 measures it.

Why

Tool results are most of a long agent's context and the cheapest thing to drop: the agent can fetch them again. The customer's words are the opposite: small, and impossible to fetch again. Make room from the side that can be rebuilt.

When clearing isn't enough: compaction

TieredCompaction is the Harness's recommended default: it clears tool results first and only summarizes older turns with a model call when clearing doesn't free enough. A summary is the one step that can drop what the customer said, so tell the summarizer what to keep. In Part 1 chapter 4 a summary that dropped the user's rule led every model to break it, 80 times out of 80.

code/part2/ch4_history.py, compaction · pydantic-ai-harness 0.68
from pydantic_ai_harness.compaction import SummarizingCompaction, TieredCompaction

compaction = TieredCompaction(
    tiers=[
        ClearToolResults(max_tokens=1, placeholder='[Cleared to save space. Call the tool again if you need it.]'),
        SummarizingCompaction(  # only when clearing isn't enough: a model call writes the summary
            model='anthropic:claude-haiku-5-5',
            max_messages=1,
            summary_prompt=(
                'Summarize this collections conversation so the agent can continue it. Keep every payment promise, '
                'correction, amount and date the customer gave, word for word.\n\n<messages>\n{messages}\n</messages>'
            ),
        ),
    ],
    target_fraction=0.7,  # of the model's context window, resolved per request
)

What you can do now

Find where your agent trims history. Replace cutting with clearing old tool results, give the cleared result a note that says how to get it back, and write your summary prompt around what your customers say.
