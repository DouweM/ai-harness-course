How harnesses are composed in Pydantic AI

The harness is everything around the model: instructions, tools, the history you keep, and the code that decides what happens next. In Pydantic AI you build it as a list: Agent(capabilities=[...]). This page is the reference for how that list turns into one request: what each capability can add, in what order, and what happens when two of them want the same thing.

Part 2, chapter 6 tells the story of why you package a harness into capabilities; the Capability gallery is where you find one. Every snippet here runs offline: uv run code/reference/composing_harnesses.py.

What one capability contributes

A capability is a class with optional methods. Each method it overrides adds one kind of thing to the agent. Capability(...) with decorators covers instructions and tools; Hooks() covers lifecycle hooks; a subclass of AbstractCapability covers everything. The right-hand column is the rule that matters once there are several.

ContributionHow a capability adds itWhen several capabilities add one
Instructionsinstructions=, @cap.instructions, get_instructions()Concatenated, sorted by how much they can change: static text first, then dynamic parts with on_change='append', then dynamic parts that rewrite. Within a tier, the agent's own come first, then each capability in list order. This keeps the start of the request stable for the prompt cache.
Tools@cap.tool, tools=, get_toolset(), get_native_tools()Combined into one toolset. Two tools with the same name are a UserError; namespace one with prefix_tools().
Which tools this request offersprepare_tools(), prepare_output_tools()Chained in list order: each sees the list the previous one returned. A tool filtered out can't be called either.
Model settingsget_model_settings(), a dict or a per-step callableLayered key by key: the model's own settings, then the agent's model_settings, then each capability in list order, then the run's model_settings. The later layer wins a key.
The modelget_model(), resolve_model_id(), get_wrapper_model() (ModelFallback, SelectModel)Selection: the last one listed that picks a model wins. Model wrappers nest, the first listed outermost.
HistoryProcessHistory, compaction, or your own before_model_requestRuns as a before_model_request hook, so in list order, each on the previous one's output. A history processor's result is kept for later requests.
Hooks around model requestswrap_model_request, before_model_request, prepare_model_request (per attempt), after_model_request, on_model_request_errorMiddleware: the first capability is the outermost layer. See the order below.
Hooks around tool callswrap_tool_execute, before_tool_execute, after_tool_execute, on_tool_execute_error, and the same for argument validationThe same middleware order, per tool call.
Run and output hookswrap_run, before_run, after_run, output validation and processing, the event streamThe same middleware order.
Per-run statefor_agent() at construction, for_run() at each run startEach capability binds itself; return a fresh instance from for_run() for state that must not leak between runs.

Instructions, tools and model settings are assembled before any model-request hook runs, so before_model_request sees the request about to be sent, tools and settings included. The collections harness below shows a real one: the agent's instructions, then the billing world's static rule, then its appended close notice, then the received date that changes on every email.

Several capabilities on one agent

The list order is the composition order. All the capabilities on an agent become one CombinedCapability that follows middleware semantics, the way web framework middleware does: every wrap_* is entered before any before_* runs, before_* hooks fire first to last, after_* hooks fire last to first. So the first capability sees the request first and the response last. Put a guard or an audit log first when it must see everything the others do, including what they change. A capability that has to sit at one position wherever it's listed declares it with get_ordering(): position='outermost' or 'innermost', wraps=[...], wrapped_by=[...], and requires=[...] for a capability that must be present. Hooks(ordering=...) takes the same constraints.

Capabilities don't call each other. To share state, put it in your deps, or have one capability emit an event another listens for.

Bundles: a capability made of capabilities

A bundle is a CombinedCapability: a capability whose parts are capabilities. Put one in an agent's list and its parts take its place, in order, so every rule above applies to the parts as if you'd listed them yourself. A capability listed after the bundle can override one of its settings, as Temperature does in your own harness below.

Three more ways to package:

  • A plain Capability is a bundle of instructions and tools, closest to a skill. With defer_loading=True it becomes an on-demand capability: a one-line catalog entry until the model loads it.
  • A WrapperCapability wraps one capability and changes some of what it does; PrefixTools is one.
  • A package: a capability published as pydantic-ai-<name>, usable from Python or an agent spec file. See publishing capabilities.

The Harness's prebuilt harnesses, Coder and Researcher, are bundles: subclasses of CombinedCapability whose constructor picks the parts.

Go deeper: bundle or list?

A list in each agent's constructor is fine for two agents. Reach for a bundle when a third agent needs the same harness, when you want flags rather than copied lists, or when you'll publish it. Either way, the request is the same: a bundle adds nothing a list doesn't.

Agents, sub-agents and delegation

An agent is a harness around a model; more than one agent is a composition of harnesses. Three shapes, from the least machinery to the most:

ShapeHowWhat the other agent gets
Agent as a toolYour tool calls other.run(...) (Part 2, chapter 7)Exactly what you pass: deps=ctx.deps, usage=ctx.usage for one budget, its own capabilities.
Sub-agentsSubAgents(agents=[SubAgent(...)]): one delegate_task tool and a roster in the instructionsThe parent's deps and, by default, its usage. Its own tools and capabilities, not the parent's; add common ones with shared_capabilities=.
Delegating to itselfSubAgents(include_self=True), as in CoderA fresh run of the same agent: everything bound to the agent, no conversation. Not what was passed to run().
