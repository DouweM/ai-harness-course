How harnesses are composed in Pydantic AI

The harness is everything around the model: instructions, tools, the history you keep, and the code that decides what happens next. In Pydantic AI you build it as a list: Agent(capabilities=[...]). This page is the reference for how that list turns into one request: what each capability can add, in what order, and what happens when two of them want the same thing.

Part 2, chapter 6 tells the story of why you package a harness into capabilities; the Capability gallery is where you find one. Every snippet here runs offline: uv run code/reference/composing_harnesses.py.

What one capability contributes

A capability is a class with optional methods. Each method it overrides adds one kind of thing to the agent. Capability(...) with decorators covers instructions and tools; Hooks() covers lifecycle hooks; a subclass of AbstractCapability covers everything. The right-hand column is the rule that matters once there are several.

ContributionHow a capability adds itWhen several capabilities add one
Instructionsinstructions=, @cap.instructions, get_instructions()Concatenated, sorted by how much they can change: static text first, then dynamic parts with on_change='append', then dynamic parts that rewrite. Within a tier, the agent's own come first, then each capability in list order. This keeps the start of the request stable for the prompt cache.
Tools@cap.tool, tools=, get_toolset(), get_native_tools()Combined into one toolset. Two tools with the same name are a UserError; namespace one with prefix_tools().
Which tools this request offersprepare_tools(), prepare_output_tools()Chained in list order: each sees the list the previous one returned. A tool filtered out can't be called either.
Model settingsget_model_settings(), a dict or a per-step callableLayered key by key: the model's own settings, then the agent's model_settings, then each capability in list order, then the run's model_settings. The later layer wins a key.
The modelget_model(), resolve_model_id(), get_wrapper_model() (ModelFallback, SelectModel)Selection: the last one listed that picks a model wins. Model wrappers nest, the first listed outermost.
HistoryProcessHistory, compaction, or your own before_model_requestRuns as a before_model_request hook, so in list order, each on the previous one's output. A history processor's result is kept for later requests.
Hooks around model requestswrap_model_request, before_model_request, prepare_model_request (per attempt), after_model_request, on_model_request_errorMiddleware: the first capability is the outermost layer. See the order below.
Hooks around tool callswrap_tool_execute, before_tool_execute, after_tool_execute, on_tool_execute_error, and the same for argument validationThe same middleware order, per tool call.
Run and output hookswrap_run, before_run, after_run, output validation and processing, the event streamThe same middleware order.
Per-run statefor_agent() at construction, for_run() at each run startEach capability binds itself; return a fresh instance from for_run() for state that must not leak between runs.

Instructions, tools and model settings are assembled before any model-request hook runs, so before_model_request sees the request about to be sent, tools and settings included. The collections harness below shows a real one: the agent's instructions, then the billing world's static rule, then its appended close notice, then the received date that changes on every email.

Several capabilities on one agent

The list order is the composition order. All the capabilities on an agent become one CombinedCapability that follows middleware semantics, the way web framework middleware does: every wrap_* is entered before any before_* runs, before_* hooks fire first to last, after_* hooks fire last to first. Two traced capabilities, A then B:

code/reference/composing_harnesses.py, two capabilities that record when they run
from pydantic_ai.capabilities import Hooks

trace: list[str] = []


def traced(name: str) -> Hooks[Deps]:
    hooks = Hooks[Deps]()

    @hooks.on.model_request  # wrap_model_request
    async def around_request(ctx, *, request_context, handler):
        trace.append(f'{name}: wrap enter')
        response = await handler(request_context)
        trace.append(f'{name}: wrap exit')
        return response

    @hooks.on.before_model_request
    async def before_request(ctx, request_context):
        trace.append(f'{name}: before')
        return request_context

    @hooks.on.after_model_request
    async def after_request(ctx, *, request_context, response):
        trace.append(f'{name}: after')
        return response

    @hooks.on.tool_execute  # wrap_tool_execute
    async def around_tool(ctx, *, call, tool_def, args, handler):
        trace.append(f'{name}: wraps {tool_def.name}')
        return await handler(args)

    return hooks


ordered = Agent('anthropic:claude-sonnet-5-5', deps_type=Deps, capabilities=[traced('A'), traced('B'), billing_world])
// output, recorded by verify.py
model request: A: wrap enter > B: wrap enter > A: before > B: before > B: after > A: after > B: wrap exit > A: wrap exit
tool call:     A: wraps lookup_invoice > B: wraps lookup_invoice

So the first capability sees the request first and the response last. Put a guard or an audit log first when it must see everything the others do, including what they change. A capability that has to sit at one position wherever it's listed declares it with get_ordering(): position='outermost' or 'innermost', wraps=[...], wrapped_by=[...], and requires=[...] for a capability that must be present. Hooks(ordering=...) takes the same constraints.

What collides, and what merges

code/reference/composing_harnesses.py, two capabilities with a lookup_invoice tool
from pydantic_ai.capabilities import Capability

ledger = Capability[Deps](id='ledger')


@ledger.tool_plain
def lookup_invoice(invoice_number: str) -> str:
    """Look up an invoice in the general ledger."""
    return f'{invoice_number}: posted'


clash = Agent('anthropic:claude-sonnet-5-5', deps_type=Deps, capabilities=[billing_world, ledger])
fixed = Agent('anthropic:claude-sonnet-5-5', deps_type=Deps, capabilities=[billing_world, ledger.prefix_tools('ledger')])

Two capabilities that bothWhat happensWhat to do
Register a tool with the same nameUserError when the run startsRename one, or wrap its capability: ledger.prefix_tools('ledger') gives ledger_lookup_invoice.

Capabilities don't call each other. To share state, put it in your deps, or have one capability emit an event another listens for.

Bundles: a capability made of capabilities

A bundle is a CombinedCapability: a capability whose parts are capabilities. Put one in an agent's list and its parts take its place, in order, so every rule above applies to the parts as if you'd listed them yourself. A capability listed after the bundle can override one of its settings, as Temperature does in your own harness below.

Three more ways to package:

  • A plain Capability is a bundle of instructions and tools, closest to a skill. With defer_loading=True it becomes an on-demand capability: a one-line catalog entry until the model loads it.
  • A WrapperCapability wraps one capability and changes some of what it does; PrefixTools is one.
  • A package: a capability published as pydantic-ai-<name>, usable from Python or an agent spec file. See publishing capabilities.

The Harness's prebuilt harnesses, Coder and Researcher, are bundles: subclasses of CombinedCapability whose constructor picks the parts.

For anything the flags don't cover (a command allowlist, a different compaction, read-only files), list the pieces yourself. The gallery's reviewer is Coder's pieces, chosen differently: it reads and runs tests but never writes. What you add next to Coder, like Permissions for approvals, composes like any other capability, and a delegate to self gets it too.

Your own harness, as a composition

Part 2's collections agent, packaged the way Coder is: a CombinedCapability whose parts are the billing world from chapter 6, a model setting, a history policy and an audit hook. Each part is one kind of contribution, and each flag is a swap.

code/reference/composing_harnesses.py, the collections harness
from pydantic_ai.capabilities import AbstractCapability, CombinedCapability
from pydantic_ai_harness.compaction import ClearToolResults


@dataclass
class Temperature(AbstractCapability[Any]):
    """Model settings, as a capability: one fixed id, so two of them on an agent merge."""

    temperature: float = 0.0
    id: str | None = 'temperature'

    def get_model_settings(self) -> ModelSettings:
        return ModelSettings(temperature=self.temperature)


class CollectionsHarness(CombinedCapability[Deps]):
    """Every agent in the collections world gets this list. Change a piece by flag, or compose your own list."""

    def __init__(self, *, audit_tools: bool = True, history: AbstractCapability[Deps] | None = None):
        parts: list[AbstractCapability[Deps]] = [
            billing_world,  # instructions and tools: Part 2, chapters 2 to 6
            Temperature(temperature=0.0),  # model settings: the same email gets the same reading
            history or ClearToolResults(max_fraction=0.7),  # history: clear old tool results past 70% of the window
        ]
        if audit_tools:
            parts.append(audit)  # a hook after every tool call
        super().__init__(parts)


collections = Agent(
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions="You handle customers' emails about their invoices with us, and record what they promise.",
    capabilities=[CollectionsHarness()],
)
reminders = Agent(  # the same harness, one setting changed by adding a capability after it
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions='Draft the reminder for this invoice, or say why none should go out.',
    capabilities=[CollectionsHarness(audit_tools=False), Temperature(temperature=0.4)],
)

Thursday during close, each agent's first request. The instructions follow the order from the table above; mark_paid is gone because the billing world's prepare hid it; and the reminders agent's Temperature, listed after the bundle, merged with the one inside it and won:

Go deeper: bundle or list?

A list in each agent's constructor is fine for two agents. Reach for a bundle when a third agent needs the same harness, when you want flags rather than copied lists, or when you'll publish it. Either way, the request is the same: a bundle adds nothing a list doesn't.

Agents, sub-agents and delegation

An agent is a harness around a model; more than one agent is a composition of harnesses. Three shapes, from the least machinery to the most:

ShapeHowWhat the other agent gets
Agent as a toolYour tool calls other.run(...) (Part 2, chapter 7)Exactly what you pass: deps=ctx.deps, usage=ctx.usage for one budget, its own capabilities.
Sub-agentsSubAgents(agents=[SubAgent(...)]): one delegate_task tool and a roster in the instructionsThe parent's deps and, by default, its usage. Its own tools and capabilities, not the parent's; add common ones with shared_capabilities=.
Delegating to itselfSubAgents(include_self=True), as in CoderA fresh run of the same agent: everything bound to the agent, no conversation. Not what was passed to run().

A dispute classifier as a sub-agent of the collections agent. It wears the same billing world, so it reads Dana's email through the parent's deps:

code/reference/composing_harnesses.py, a sub-agent in the same world
from pydantic_ai_harness.subagents import SubAgent, SubAgents

disputes = Agent(
    'anthropic:claude-haiku-5-5',
    name='disputes',
    description='Decides whether a customer email disputes one of our invoices.',
    deps_type=Deps,
    instructions='Read the email and say whether it disputes an invoice, and which amount.',
    capabilities=[billing_world],  # the same world: read_email, lookup_invoice, the close rule
)
lead = Agent(
    'anthropic:claude-sonnet-5-5',
    deps_type=Deps,
    instructions="You handle customers' emails about their invoices with us.",
    capabilities=[CollectionsHarness(), SubAgents(agents=[SubAgent(disputes)])],  # adds delegate_task
)
// output, recorded by verify.py
lead tools offered: ['read_email', 'lookup_invoice', 'mark_paid', 'record_payment', 'delegate_task']
lead output: Handed to a person: INV-2041 is disputed: the customer says they were quoted 3,900.
requests counted on the lead run (lead and delegate): 4

Four requests: two from the lead, two from the delegate, counted on one usage, so a UsageLimits on the lead bounds the whole tree. A handoff, where the run ends and your code routes the case, is an output type rather than a capability; chapter 7 shows it. For a whole graph of agents, see multi-agent applications.
