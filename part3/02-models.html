Why it matters for choosing

Clearing old tool results is a reasonable harness choice for the larger models: it notices the hole and fills it with a tool call. For the smaller model the same choice is a bug factory. Neither model is wrong; the configuration is. With the smaller model you keep the results, require the lookup before the write, or validate the value against the ledger, and you pay for that in harness work and in evals.

Freeze what works, per family

An instruction function can branch on ctx.model, but after a ModelFallback it still sees the model the step started on (#12747); first-class per-model instructions are being designed (#12545). Don't wait: keep one frozen agent spec per family, and treat a new model as a candidate.

  1. Copy the closest frozen spec; change only the model.
  2. Run your eval set (chapter 3) and read what it gets wrong.
  3. Fix those cases for this family, one line at a time.
  4. When it matches the frozen spec on the cases you care about, freeze it.
  5. Roll it out to part of the traffic, watch, then all of it.

The specs below are for the email classifier chapter 3 evaluates, promise_router: given one email, it fills Part 2's answer form plus two fields, addressed_to_us (is the promise made to us, not to someone else?) and evidence (the email's own words that back the answer).

model_settings:
  max_tokens: 2000

A capability that branches on ctx.model today sees the model the step started on, not a fallback; that's what #12747 fixes.

Go deeper: falling back per request, not per run

ModelFallback moves one request to the next model, when it fails, is refused or is cut off, and the run carries on with everything the first model already did in its history. That's right for an outage. It doesn't cover the failures that show up later: an answer that fails your output validator, or a tool call with side effects that the first model already made. Those end in your code, where you decide whether to rerun the whole run on another model. To stay on the model that answered for the rest of the run and the conversation's later runs, pass sticky=True.

A new model is a candidate, not an upgrade.

Roll out without a redeploy

ManagedPrompt (Pydantic AI Harness) reads the instructions from a Logfire-managed prompt: version and label it in Logfire, roll a change out to part of the traffic, roll it back from the UI. Every span records which label produced it.

code/part3/ch2_model_configs.py · pydantic-ai-harness[logfire]
claude_spec = AgentSpec.from_file(CONFIGS / 'claude-5.yaml')
managed = Agent(
    output_type=PaymentCommitment,
    capabilities=[ManagedPrompt('promise_router', default=str(claude_spec.instructions), label='production')],
)

A pinned label stays fixed between rollouts and keeps the prompt cache warm. For a share-of-users rollout, leave label unset and pass a targeting_key, so each user always gets the same label. The default is used until a prompt is published.
