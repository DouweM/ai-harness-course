Part 3 · Production, and measuring what works

Production architectures

An agent run lives in your server's memory, so when the server stops or restarts, the run stops too; the saved conversation is what survives. So a run that waits for a person ends and starts again later, every write is safe to repeat, and every run leaves a trace (a record of its model requests and tool calls).

One payment request, Friday to Monday

Friday 20 Nov, 17:40The bank confirms the first half of Dana's wire, sent that morning. Part 2's billing agent asks to record 2,060.00 against INV-2041, and record_payment needs a person (Part 2, chapter 6). Nobody approves until Monday. Over the weekend the ledger has an outage and you deploy.

Two questions decide how it runs. How does the run begin, and who is waiting? The bank's confirmation, and nobody: it is a job on the task queue you already run. What does a crash cost? Two model requests and one payment written with an idempotency key (an id sent with the write, so the ledger ignores a repeat of the same request). Starting again is fine, so this agent needs no durable engine: a system that saves each finished step and resumes from there after a crash. An engine pays off when runs are long or a side effect can't be safely repeated (the DBOS version below). Step through the week:

If the ledger were still down on Monday

Part 2 chapter 3 sorted tool errors into the model's mistake (ModelRetry), your outage (ToolFailed) and a normal answer. Production is where the middle one earns its keep: an approval that lands during an outage must not turn into "recorded" in the reply drafted for Dana.

Killed before the result was saved. Monday's run starts again from the stored conversation and the same approval, so call_fri_1740 runs again with the same arguments.

The tool runs twice; the ledger holds one payment. The replayed call has the same tool call ID, so the ledger returns its first answer. Nothing can roll back a call to someone else's API, and without a key the ledger can't tell a replay from a new payment. The ID comes back unchanged because it is part of what you resume from (the stored conversation here, the journal on DBOS), so ctx.tool_call_id is the natural key for a write the run resumes into.

A retry that starts the run over is different: the model is asked again and picks a new tool call ID, so the key can't catch the repeat. For writes made inside the first run, like the small-payments policy below, key on something a retry can't change, such as the bank's wire reference.

Go deeper: where the steps are, and a ledger that takes no key

With DBOSDurability, each model request and each MCP call is a journaled step: a crash replays finished steps from the journal and re-runs only what was in flight, which is why the model's tool call, and its ID, come back unchanged. Your own function tools are not steps unless you mark the I/O they do: a @DBOS.step function your tool calls with plain arguments (the invoice number, the amount, the key), rather than the tool itself, so a finished call isn't repeated on recovery; and keep deps serializable. The step that was in flight when the process died can still run twice, so every write needs the key. If your system of record takes no idempotency key, keep one on your side: a table keyed on tool_call_id, written in the same transaction as your own record of the payment, and checked before calling out. A call that reached the other system but never got recorded on yours still needs a reconciliation job; no key fixes a write you can't see.

Between starting again and an engine, StepPersistence (Harness) snapshots the history at each tool-call boundary and records which tool calls may have run, so you can continue a crashed run without an engine.

Waiting ends the run

Part 2 built the waiting: the run ends with DeferredToolRequests, you store the Conversation, and a new run continues it with the person's decision. Production adds two things. When only some calls need a person, the cleanest gate is conditional: register an args_validator= that raises ApprovalRequired() only for amounts over 1,000, so small payments never become a question and bad arguments never reach anyone. When something else answers approvals in process (a policy, a bot, a second model), HandleDeferredToolCalls runs it inside the run, so a person only sees the ones that need a person:

code/part3/ch1_weekend.py, a policy
async def small_amounts(ctx: RunContext[Deps], requests: DeferredToolRequests) -> DeferredToolResults | None:
    """Approve payments up to 1,000 inside the run; return None for the rest, so they wait for a person."""
    small = {c.tool_call_id: True for c in requests.approvals if Decimal(str(c.args_as_dict()['amount'])) <= 1000}
    return requests.build_results(approvals=small) if small else None

collections.run(..., capabilities=[HandleDeferredToolCalls(small_amounts)])
  INV-2057 980.00: approved by the policy  payments: [('INV-2057', Decimal('980.00'))]
  INV-2041 2060.00: waits for a person  payments: []

When a crash would cost more than a rerun, or the workflow itself should hold the wait, put the run on a durable engine. It journals each model request and tool call, so a crash anywhere replays what finished:

The durable version (DBOS)

The docs' end-to-end service, without the HTTP routes and runnable offline. The workflow itself waits up to a week for the decision; on restart DBOS replays what finished. Temporal, Prefect and Pydantic AI Harness's Postgres engines (Absurd, pgtask) attach the same way, as a capability; Restate wraps the agent in its own class. A policy handler without a resume token isn't journaled, so it reruns on replay. A deploy changes what in-flight runs replay against: let them drain, or follow the engine's versioning guidance.

@DBOS.workflow()
async def collections_run(prompt: str) -> str:
    result = await agent.run(prompt)
    while isinstance(output := result.output, DeferredToolRequests):
        pending = {call.tool_call_id: call.args_as_dict() for call in output.approvals}
        await DBOS.set_event_async('state', {'status': 'awaiting_approval', 'pending': pending})
        approvals: dict[str, bool] | None = await DBOS.recv_async('approvals', timeout_seconds=7 * 24 * 3600)
        if approvals is None:  # nobody answered within a week
            approvals = {call_id: False for call_id in pending}
        result = await agent.run(
            conversation=result.conversation,
            deferred_tool_results=output.build_results(approvals=approvals),
        )
    await DBOS.set_event_async('state', {'status': 'done', 'output': output})
    return output

Approval is a stored conversation, not a sleeping process.
