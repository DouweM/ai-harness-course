What happened

One payment. The replayed call has the same tool call ID, so the ledger returns its first answer.

Monday 09:15, approved: Tool said: Recorded 2060.00 on INV-2041.
  crash, same call again: tool ran twice, payments recorded: [('INV-2041', Decimal('2060.00'))]

Run it: uv run code/part3/ch1_weekend.py. Deterministic, no model calls. The idempotency key is Part 2's ctx.tool_call_id in billing_world.py.

Why

Nothing can roll back a call to someone else's API, and without a key the ledger can't tell a replay from a new payment. ctx.tool_call_id survives the replay because the model's response comes from the journal, so it is the natural idempotency key for every write.

Waiting ends the run

Part 2 built the waiting: the run ends with DeferredToolRequests, you store the Conversation, and a new run continues it with the person's decision. Production adds two things. A policy can answer some approvals inside the run, so a person only sees the ones that need a person:

code/part3/ch1_weekend.py, a policy
async def small_amounts(ctx: RunContext[Deps], requests: DeferredToolRequests) -> DeferredToolResults | None:
    """Approve payments up to 1,000 inside the run; return None for the rest, so they wait for a person."""
    small = {c.tool_call_id: True for c in requests.approvals if Decimal(str(c.args_as_dict()['amount'])) <= 1000}
    return requests.build_results(approvals=small) if small else None

collections.run(..., capabilities=[HandleDeferredToolCalls(small_amounts)])
  INV-2050 980.00: approved by the policy  payments: [('INV-2050', Decimal('980.00'))]
  INV-2041 2060.00: waits for a person  payments: []

And a durable engine can hold the wait itself, journaling each model request and tool call so a crash anywhere replays what finished:

The durable version (DBOS)

The docs' end-to-end service, without the HTTP routes and runnable offline. The workflow itself waits up to a week for the decision; on restart DBOS replays what finished. Temporal, Restate, Prefect and the Harness's Postgres engines attach the same way. A deploy changes what in-flight runs replay against: let them drain, or follow the engine's versioning guidance.

@DBOS.workflow()
async def collections_run(prompt: str) -> str:
    result = await agent.run(prompt)
    while isinstance(output := result.output, DeferredToolRequests):
        pending = {call.tool_call_id: call.args_as_dict() for call in output.approvals}
        await DBOS.set_event_async('state', {'status': 'awaiting_approval', 'pending': pending})
        approvals: dict[str, bool] | None = await DBOS.recv_async('approvals', timeout_seconds=7 * 24 * 3600)
        if approvals is None:  # nobody answered within a week
            approvals = {call_id: False for call_id in pending}
        result = await agent.run(
            conversation=result.conversation,
            deferred_tool_results=output.build_results(approvals=approvals),
        )
    await DBOS.set_event_async('state', {'status': 'done', 'output': output})
    return output

Approval is a stored conversation, not a sleeping process.
