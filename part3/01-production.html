Part 3 · Production, and measuring what works

Production architectures

An agent run lives in server memory and stops when the server stops. The saved conversation survives. A run waiting for a person ends and starts again later, every write is safe to repeat, and every run leaves a trace (a record of its model requests and tool calls).

One payment request

The bank confirms the first half of Dana's wire. Part 2's billing agent asks to record 2,060.00 against INV-2041, and record_payment needs a person (Part 2, chapter 6). Meanwhile, the ledger has an outage and you deploy.

How does the run begin, and who is waiting? The bank's confirmation starts a job on your task queue; nobody waits on the run. What does a crash cost? Two model requests and one payment written with an idempotency key (an id sent with the write, so the ledger ignores a repeat of the same request). Starting again is fine, so this agent needs no durable engine: a system that saves each finished step and resumes from there after a crash. An engine helps when runs are long or a side effect cannot be safely repeated (see the DBOS version below). Step through:

Killed before the result was saved. The run restarts from the stored conversation and approval, so call_fri_1740 runs again with the same arguments.

The tool runs twice; the ledger holds one payment. The replayed call has the same tool call ID, so the ledger returns its first answer. A call to another API cannot be rolled back, and without a key the ledger cannot distinguish a replay from a new payment. The ID stays the same because it is part of the resumed state (the stored conversation here, the DBOS journal), making ctx.tool_call_id a natural key for resumed writes.

A retry that starts the run over is different: the model is asked again and picks a new tool call ID, so the key cannot catch the repeat. For writes inside the first run, such as the small-payments policy below, use a key that a retry cannot change, such as the bank's wire reference.

Go deeper: where the steps are, and a ledger that takes no key

With DBOSDurability, each model request and MCP call is a journaled step. After a crash, finished steps replay from the journal and only the in-flight step runs again; the model's tool call and ID stay unchanged. Your function tools are not steps unless you mark their I/O: call a @DBOS.step function with plain arguments (invoice number, amount, key), rather than wrapping the tool, so finished work is not repeated on recovery. Keep deps serializable. The in-flight step can still run twice, so every write needs a key. If your system of record accepts no idempotency key, keep one in your own table keyed on tool_call_id, write it in the same transaction as your payment record, and check it before calling out. If the other system receives a call that your table misses, a reconciliation job is still needed; no key fixes an unseen write.

Between starting again and an engine, StepPersistence (Harness) snapshots the history at each tool-call boundary and records which tool calls may have run, so you can continue a crashed run without an engine.

Waiting ends the run

Part 2 established the waiting pattern: the run ends with DeferredToolRequests, you store the Conversation, and a new run continues with the person's decision. Production adds two options. To require approval only for some calls, register an args_validator= that raises ApprovalRequired() for amounts over 1,000; small payments proceed, and invalid arguments stop before approval. To handle other approvals in process (with a policy, bot, or second model), use HandleDeferredToolCalls; a person sees only the calls that need them:

code/part3/ch1_weekend.py, a policy
async def small_amounts(ctx: RunContext[Deps], requests: DeferredToolRequests) -> DeferredToolResults | None:
    """Approve payments up to 1,000 inside the run; return None for the rest, so they wait for a person."""
    small = {c.tool_call_id: True for c in requests.approvals if Decimal(str(c.args_as_dict()['amount'])) <= 1000}
    return requests.build_results(approvals=small) if small else None

collections.run(..., capabilities=[HandleDeferredToolCalls(small_amounts)])
  INV-2057 980.00: approved by the policy  payments: [('INV-2057', Decimal('980.00'))]
  INV-2041 2060.00: waits for a person  payments: []

Use a durable engine when a crash costs more than a rerun or the workflow must hold the wait. It journals model requests and tool calls, then replays finished steps after a crash:

The durable version (DBOS)

This is the docs' end-to-end service without HTTP routes, runnable offline. The workflow waits up to a week for a decision; after restart, DBOS replays finished steps. Temporal, Prefect and Pydantic AI Harness's Postgres engines (Absurd, pgtask) attach as capabilities; Restate wraps the agent in its own class. A policy handler without a resume token is not journaled and reruns on replay. Deploys change the code used by in-flight runs: let them drain or follow the engine's versioning guidance.

@DBOS.workflow()
async def collections_run(prompt: str) -> str:
    result = await agent.run(prompt)
    while isinstance(output := result.output, DeferredToolRequests):
        pending = {call.tool_call_id: call.args_as_dict() for call in output.approvals}
        await DBOS.set_event_async('state', {'status': 'awaiting_approval', 'pending': pending})
        approvals: dict[str, bool] | None = await DBOS.recv_async('approvals', timeout_seconds=7 * 24 * 3600)
        if approvals is None:  # nobody answered within a week
            approvals = {call_id: False for call_id in pending}
        result = await agent.run(
            conversation=result.conversation,
            deferred_tool_results=output.build_results(approvals=approvals),
        )
    await DBOS.set_event_async('state', {'status': 'done', 'output': output})
    return output

Approval is a stored conversation, not a sleeping process.
